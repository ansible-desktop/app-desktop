# Сервис обновлений Ansible Desktop

Отдаёт клиентам манифест и пакеты обновлений по `https://ansible.su/ad/`.

```
клиент                    ansible.su/ad          Timeweb S3
  |                         (as-updates)     ansible-desktop-updates
  |  GET /ad/current2  ------->  proxy  ------->  current2
  |  <--- {"win64":{"stable":{"released":3003001,"link":"/win64/…"}}}
  |
  |  своё AppVersion = 3003000, пришло 3003001 -> обновление есть
  |
  |  GET /ad/win64/tx64upd3003001 -->  proxy  --> объект win64/tx64upd3003001
  |  <--- пакет (качается кусками, Range)
  |
  |  проверяет подпись Ed25519, распаковывает в tupdates/ready
  |  при следующем запуске Updater.exe подменяет файлы
```

## Из чего состоит

| часть | где |
|---|---|
| раздача | под `as-updates` в namespace `ansible-apps`, тонкий nginx-прокси |
| маршрут | ingress `as-updates`, путь `/ad` на хосте `ansible.su` |
| хранилище | Timeweb S3, бакет `ansible-desktop-updates`, публичный на чтение |
| манифест | объект `current2` в том же бакете |
| пакеты | объекты `<платформа>/<имя>`, например `win64/tx64upd3003001` |

Манифесты кластера — [`as-updates.yaml`](as-updates.yaml), применяются
`kubectl apply -f`. Генератор манифеста выпусков — [`make_current.py`](make_current.py).

## Почему именно так

**Почему прокси, а не прямая ссылка на S3.** Адрес пакета клиент строит как
`<префикс> + link` (`core/update_checker.cpp`, `HttpChecker::handleResponse`),
то есть он всегда под `https://ansible.su/ad`. Положить в `link` абсолютный
внешний адрес нельзя — получится склейка `https://ansible.su/adhttps://…`.

**Почему бакет публичный.** Пакеты и так предназначены всем, а их целостность
держится не на секретности ссылки, а на подписи Ed25519: корневой открытый
ключ вшит в клиент (`Ansible/Resources/update/root-public.pem`), подпись
покрывает в том числе целевую платформу, поэтому пакет для x64 нельзя
подсунуть arm-клиентам.

🚨 **Ключи Timeweb общие на весь аккаунт.** Одна и та же пара читает и
приватный бакет `ansible-cdn-ciphertext`. Именно поэтому в кластере их нет:
публичный бакет позволяет обойтись без секрета в поде. Держать ключи только
в Vault, в репозиторий и в манифесты не класть.

## Ключи подписи

Корень доверия наш, отчеканен 25.09.2026. До этого `Ansible/Resources/update/`
целиком приехал ребейзом с upstream 7.2.8: корневой ключ и манифест
принадлежали Телеграму, приватные половины — им же. Подписать обновление не
могли ни мы, ни кто-либо кроме них.

| что | где лежит приватная половина |
|---|---|
| корневой Ed25519 | Vault `secret/ansible/desktop/updates_root_private` |
| ключ канала `as-stable-2026a` | Vault `secret/ansible/desktop/updates_stable_2026a_private` + секрет GitHub `UPDATES_SIGNING_KEY` |

Публичные половины и манифест лежат в репозитории и вшиваются в клиент:
`Ansible/Resources/update/{root-public.pem, manifest.min.json, manifest.sig}`.

🚨 **Корневой ключ в CI не кладём никогда.** Им подписывается только сам
манифест — то есть при заведении или отзыве ключа канала, это редкая ручная
операция. В сборке участвует ТОЛЬКО ключ канала. Если утечёт ключ канала —
вносим его в `revoked`, чеканим новый и пересобираем клиент. Если утечёт
корневой — меняется корень, а значит и все установленные клиенты перестают
доверять обновлениям и требуют переустановки.

**Почему один ключ на stable и beta.** В манифесте канал задан группой из
одного ключа, поэтому выпуск — один проход упаковщика с `-local-key`. Схема
апстрима требовала двух подписей (Ed25519 локально плюс ES256 из Azure Key
Vault), и второй подписант нам сейчас не нужен. Захотим разделить — это
правка манифеста и его переподпись корнем.

**Каналы canary не объявлены** намеренно: мы их не выпускаем, а необъявленный
канал клиент не примет.

🚨 **Срок годности ключам НЕ ставим.** Принудителен только `expires` у КЛЮЧА
(`core/update_verify.cpp:809`); `expires` самого манифеста клиент разбирает,
но ни с чем не сравнивает. Забытая дата у ключа в тихий день выключила бы
обновления всем сразу, а рычаг отзыва у нас и так есть — список `revoked`.

**Старая пара `updates_private.pem` / `updates_public.pem`** (RSA-1024) — от
схемы v1 и больше ни на что не годится: упаковщик v2 принимает только
Ed25519, а путь v1 закрыт вшитыми в упаковщик публичными ключами апстрима.
Удалить после того, как убедимся, что она нигде не упомянута.

## Как выпустить новую версию

Допустим, актуальна 0.3.0, выпускаем 0.3.1.

1. **Поднять версию** — одним скриптом, он патчит все пять файлов сразу:

   ```
   python Ansible/build/set_version.py 0.3.1
   ```

   Добавить запись в `changelog.txt` первой строкой: `0.3.1 (дата)`.

2. **Собрать** — пуш в `dev` поднимает быструю сборку Windows, пуш в `master`
   собирает всю матрицу. Скачать артефакт.

3. **Упаковать и подписать.** Упаковщик — `Ansible/SourceFiles/_other/packer.cpp`,
   цель `Packer` в сборке. Он берёт каталог с готовыми файлами и приватный
   ключ (`ansible-desktop/updates_keys/updates_private.pem`, вне этого
   репозитория) и пишет пакет с именем вида `tx64upd3003001`.

   🚨 Версия в имени — **целое** `AppVersion`, а не строка «0.3.1»: 0.3.1
   это 3003001. Схема — `3000000 + minor*1000 + patch`.

4. **Залить пакет** в бакет под ключом `<платформа>/<имя пакета>`:

   ```
   win64/tx64upd3003001
   ```

   Заливать с `Cache-Control: public, max-age=31536000, immutable` — пакет
   на конкретной версии неизменяем.

5. **Обновить манифест** — и только ПОСЛЕ того, как пакет уже лежит:

   ```
   python deploy/updates/make_current.py --version 0.3.1 \
       --platform win64 --platform linux > current2
   ```

   Залить `current2` с `Content-Type: application/json` и
   `Cache-Control: public, max-age=60`.

6. **Проверить снаружи**, а не по логу заливки:

   ```
   curl -s https://ansible.su/ad/current2
   curl -sI https://ansible.su/ad/win64/tx64upd3003001
   ```

🚨 **Порядок шагов 4 и 5 менять нельзя.** Манифест, объявивший версию,
пакета которой ещё нет, отправляет клиентов за файлом, которого нет; S3
отвечает на это `403`, и клиент показывает ошибку обновления.

## Что клиент делает с пакетом

Скачанный пакет не является установщиком. Клиент проверяет подпись,
распаковывает файлы во временный каталог и кладёт рядом отметку готовности
(`UnpackUpdate` → `WriteUpdateReadyFile`). Подмена файлов происходит при
следующем запуске, её выполняет `Updater.exe`. Поэтому обновление всегда
требует перезапуска приложения, а сорванная закачка не оставляет
полуобновлённой установки.

## Известные шероховатости

- **Нет объекта — S3 отвечает `403`, а не `404`.** Так устроен публичный
  бакет без права листинга. При разборе «почему не обновляется» это читается
  как проблема доступа, хотя на деле файла просто нет.
- **Имена пакетов достались от апстрима**: `tupdate`, `tx64upd`, `tmacupd`,
  `tlinuxupd` — буква `t` здесь от Telegram. Имя берётся из `link`, так что
  клиенту оно безразлично; переименовать можно, но одновременно в упаковщике
  (`packer.cpp`) и в `make_current.py`.
- **Адрес обновлений может задаваться сервером.** Поле
  `autoupdate_url_prefix` (flags.7) в `help.getConfig` пишется клиентом в
  `tdata/prefix` и перебивает вшитое значение. Наш бэкенд его сейчас не
  шлёт, поэтому работает строка из `storage/localstorage.cpp`.
